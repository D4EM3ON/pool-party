### Notes:
- The `sandwich` package, with a specific set of data (notably, a cliff - see [`src/_common/data.r`](src/_common/data.r), line 16) produces a stack overflow: `sandwich::pava.blocks()` fails with `Error: node stack overflow` from around $N = 2500$.
- Both `UniIsoRegression::reg_1d` and `monotone::legacy(number = 13)` (the latter being supposed to be an implementation of the earlier under the `monotone` package) have errors. See them in action under [`src/_validation/error-visualisation.r`](src/_validation/error-visualisation.r)
  - The original seems to count the first element twice whenever a pooled block reaches the start of the vector. This seems to be corrected in the `monotone` package, but makes the original wrong whenever a pooled block reaches the first element.
  - The legacy version initializes a vector with all zeros (`mean_vec`), and never sets it out to what it is supposed to be originally (`x`). This causes values that are already in order, in some cases, to be pooled together, becoming wrong whenever the data has values that should not be ppoled.
- `orthoMTL::nnmaxheap_C()` on version 0.1.0 gives wrong results whenever a pooled block has a single element, even on data that is already in order: `nnmaxheap_C(c(3, 2, 1))` returns `3 3 3`, and its own documented example `nnmaxheap_C(c(5, 3, 3, 1))` returns `5 5 5 1` instead of being unchanged.
  - The PAVA pass itself is correct; the bug is in the final loop that expands the blocks: `for (j in (i + 1):location[i])`. For a single-element block, `location[i] == i`, so `(i + 1):i` counts down to `c(i + 1, i)` instead of being empty, and overwrites the start of the next block with the current value. Using `seq.int(i + 1, length.out = location[i] - i)` would fix it.


We assume `quadprog::solve.QP` to be the source of truth here. For all of its results, all functions in all packages have (within approximately $1.5\times 10^{-8}$) the same results.

Versions and dates for the packages and functions used for the results are available in [VERSIONS.md](results/VERSIONS.md)


### Adding a new function

All commands are run from the repo root (paths are relative to it).

1. Copy `src/_template/` to `src/<package>/`
2. Adapt `data.r` and `plots.r` to the function. The function must take a vector `x` and return the **increasing** fit.
3. If installing it is more than `install.packages()`, add the steps to [`docs/INSTALLATION.md`](docs/INSTALLATION.md).
4. Validate: add the function to `isotonic_functions` in [`src/_validation/data.r`](src/_validation/data.r), rerun it (it can take a while), then rerun `src/_validation/plots.r`.
5. Run `src/<package>/data.r`, then `src/<package>/plots.r`
6. Add the results as an appendix to a new entry in [`entries/`](entries/):
   - Copy [`entries/_template.md`](entries/_template.md) to `entries/YYYY-MM-DD.md`
   - Modify the day and the description
   - Uncomment the appendix, and add the package name as a subheader, then copy-paste the results figures (`figure.png` and `figure-ref.png`) under this subheader
7. Add the function in alphabetical order to:
   - the table in [`README.md`](README.md)
   - [`results/FUNCTIONS.md`](results/FUNCTIONS.md): worst- and best-case complexities for both space and time
   - [`results/VERSIONS.md`](results/VERSIONS.md): the version of the package tested in the repo, and its date
   - [`results/PAPER_COMPARISON.md`](results/PAPER_COMPARISON.md): whether it is in Busing (2022) / Mair (2009), else leave empty
8. If the function is $O(N)/O(N\log N)$ time in worse-case, add it to [`src/_best/data.r`](src/_best/data.r) and rerun it + [`src/_best/plots.r`](src/_best/plots.r)
